# 设计审查原则

本文是 [01-constitution.md](01-constitution.md) 的审查工具。

它不定义新的系统本体，也不替代宪法条文。它的职责是帮助我们判断：一个新设计究竟应该进入宪法、进入释义文档、进入实现指南，还是根本不应进入主路径。

若本文与宪法冲突，以 [01-constitution.md](01-constitution.md) 为准。

## 1. 审查顺序

面对一个新设计，优先按下面四步审查：

1. **先判法阶**
   它是在定义最小本体、权力边界、默认法律效力或不可破坏关系，还是只是在解释、审查、实现或演示？

2. **再判平面**
   它主要落在 Agent、Turn、完整语义中的哪个平面？还是在描述 projection、notification、runtime、operator surface 等下位结构？

3. **再判权力与效力**
   它让谁获得什么正式控制权？让什么材料获得什么默认法律效力？这种效力是否被显式建模？

4. **最后判实现是否上浮**
   它是否把接口命名、当前实现习惯、当前 runtime 分工、demo 结构或临时 workaround 伪装成了公理？

如果第一步就发现这不是“宪法内容”，就不应把它写入 [01-constitution.md](01-constitution.md)。

## 2. 入主路径前的十个问题

任何新设计进入主路径前，至少要先回答：

1. 这是宪法、释义、审查原则，还是实现/集成文档？
2. 它属于 Agent、Turn、完整语义中的哪一个平面？
3. 它是在保存 truth，还是在生成 projection？
4. 它是否把宿主、进程、容器、会话或网络端点提升成正式主体？
5. 它让谁获得什么控制权？该控制权来源是否被显式建模？
6. 它是否把能力、可用性、健康、接活意愿或其他观察信号误当成授权？
7. 它是否让 requester、parent、observer 或 operator 自动获得后续控制权？
8. 它试图让什么对象获得什么默认法律效力？这种效力是否已经被显式建模？
9. 它是否让旧 Turn 历史、projection、push 通知或 mere persistence 偷偷升级为 continuity、identity、authorization 或 contract effect？
10. 这条规则能否被下位设计、实现与审查直接验证？

## 3. 宪法条文应如何写

好的宪法条文，通常应同时包含三层：

1. **正面定义**
   这个对象是什么，它积极建立了什么秩序。

2. **边界限制**
   它不当然意味着什么，它不自动替代什么。

3. **规范后果**
   因此，什么效力成立，什么效力默认不成立。

如果一条条文只剩下否定句，它通常不够有建制意义。

如果一条条文主要在列接口、命名空间、字段、当前数据结构或 demo 路径，它通常已经不是宪法。

## 4. 本体与边界审查

### 4.1 不要把实现细节写成本体

下面这些东西通常不应直接写进宪法：

- 字段名
- HTTP 路径
- 命名空间前缀
- parser 约定
- 当前 runtime 分工
- 临时目录结构
- demo 名字

如果某个实现细节真的重要到值得长期约束，应先把它重新表述成：

- 本体定义
- 权力边界
- 默认法律效力
- 或不可破坏关系

否则它就不应入宪。

### 4.2 不要把策略空间提前冻结

宪法应约束“哪些边界必须成立”，而不是预先决定“唯一允许的实现形态”。

例如，合法的宪法命题会是：

- 控制权来源必须显式
- 历史材料默认不自动具有效力
- child 不得直接改写 parent

而过早冻结实现形态的说法通常会像：

- 只能用某一种 routing 方式
- 只能在出生时绑定某一种具体实体
- 只能通过某一种数据载体表达 contract effect

这些内容通常应下沉到释义或实现层。

## 5. 权力与授权审查

### 5.1 发起、观察与控制必须分离

如果一个设计默认“谁发起，谁后续可写、可停、可恢复”，它应被视为隐式权力扩张。

如果一个设计默认“谁看到了历史，谁就有权继续控制”，它也应被视为边界越界。

### 5.2 能力不等于授权

如果一个设计把下面这些东西直接解释成控制权来源，应被拒绝或重建：

- capability
- 可用性
- 健康
- 最近活动
- 接活意愿
- 某种聚合分数

这些都可以帮助 admission、routing 与理解系统，但它们本身不等于授权。

### 5.3 Kernel 不代作策略判断

如果一个设计要求 kernel 自动判断：

- 某个 child 结果是否满足业务要求
- 某个 parent 是否应该恢复
- 某个外部事实是否应被吸收
- 某个复杂编排是否已经成功

它就已经在把策略层回灌进 kernel。

## 6. 默认法律效力审查

### 6.1 可读不等于自动有效

“能读到”不等于“自动有法律效力”。

系统中尤其要警惕下面几类材料被偷偷升级：

- 旧 Turn 历史
- semantic / context / feed
- progress / 过程记录
- projection
- push 通知
- mere persistence

如果某种关键效力只是因为某条记录被保存、能被 parser 找到、或者恰好位于某个字段位置而成立，这种设计通常已经违背宪法。

### 6.2 默认效力与显式建模

旧 Turn 历史默认只应被视为：

- inspect 材料
- audit 材料
- reference 材料
- shared observation

如果一个设计试图让这类材料承担：

- continuity
- identity proof
- authorization proof
- contract effect
- kernel correctness 前提

它必须把这种效力显式建模。

### 6.3 Agent-native memory 边界

如果一个设计在默认情况下把 CommonGround 推定为：

- session continuity 真源
- 内部思考真源
- 长期记忆真源
- runtime-local 工作内态真源

它就已经越过了当前宪法确立的边界。

## 7. Projection、Push 与历史材料

### 7.1 Projection

Projection 可以强大、丰富、产品化。

但 projection 的强大不意味着它可以反向定义 truth。

如果一个设计的论证方式是“dashboard 需要这样显示，所以 kernel truth 必须这样建”，应被拒绝或重新建模。

### 7.2 Push

Push 只能是加速层。

如果一个设计在通知丢失时无法恢复，它就不应进入 kernel correctness 路径。

### 7.3 历史材料

读取旧历史可以是合法而有价值的：

- 当前 Turn 恢复判断
- 审计
- review
- operator 观察
- shared observation 吸收

需要被限制的不是“读取”本身，而是“读取后自动获得未建模效力”。

## 8. 什么时候该修宪

以下情况更可能需要修宪：

- 出现了新的最小本体
- 出现了新的不可破坏关系
- 出现了必须长期承认的新默认法律效力
- 旧条文与长期实现之间持续存在不可回避的冲突

以下情况通常不应优先修宪：

- 当前实现不方便
- 某条接口命名已经被广泛使用
- 某个 demo 很顺手
- 某种 parser 或 schema 临时够用
- 希望把尚未验证的策略空间提前写死
